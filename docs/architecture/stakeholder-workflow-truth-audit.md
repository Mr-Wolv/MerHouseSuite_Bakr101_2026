# Stakeholder Workflow Truth Audit

This document owns the V15.10 stakeholder-by-stakeholder workflow truth audit. The goal is to determine whether MerHouse works as the intended role-aware fulfillment coordination system, not merely whether the current screens and tests pass.

V15.10 starts from the human concern that the app can feel baffling when trying to understand how actions move back and forth between stakeholders. The audit must therefore answer four questions for each stakeholder:

- What is this stakeholder supposed to do?
- What actions can they take, and what should those actions change elsewhere?
- Is the implementation correct, authorized, visible, tested, and recoverable?
- Did we implement the right thing, or did we build a technically valid workflow that is awkward, one-sided, redundant, or impossible to operate?

This audit does not claim production SaaS readiness. Provider-backed delivery, realtime infrastructure, monitoring, stress/load, backup/restore, and real deployment activation remain V16 local certification or later V17 work.

The phase target is planning-grade maturity: by closeout, MerHouse should be ready to enter the final Pre-V16 quality-control gate because stakeholder loops are documented, coherent, locally operable, covered by current tests, supported by current scripts, and backed by proof. Any remaining uncertainty should be explicit enough to become a Pre-V16 blocker, V16 deployment-ready local certification item, or later real deployment activation item.

## Audit Method

For each stakeholder, complete the same pass:

1. Intent: describe the stakeholder's real product job in plain language.
2. Routes: list the routes and panels they should use for daily work.
3. Actions: list each create, update, approve, reject, advance, resolve, review, read, or diagnostic action available to the stakeholder.
4. Backend contract: map each action to the service/API path, persisted object, audit record, outbox event, notification, attention signal, and downstream read path it should affect.
5. Counterparty effect: state who else should see the change, where they should see it, and whether they can respond.
6. Browser truth: run the workflow in the live app with seeded local accounts and record whether the user-facing result is understandable.
7. Test truth: identify existing tests, missing tests, stale assertions, and any new proof needed.
8. Docs/scripts truth: identify whether README, architecture docs, development docs, seed scripts, quality scripts, and browser/E2E scripts still describe and prove the workflow correctly.
9. Product verdict: classify the workflow as sound, implemented-but-confusing, implemented-but-wrong-owner, incomplete, impossible, redundant, or deferred-to-Pre-V16.

## Stakeholder Order

| Order | Stakeholder | Primary question |
| --- | --- | --- |
| 1 | Public requester and recovery user | Can a non-authenticated user request access or recover an account without fake production claims or confusing next steps? |
| 2 | Owner/platform admin | Can the owner govern tenants, users, access requests, reliability, service exceptions, audit, notifications, and assistant review without daily work being mixed into evidence-only pages? |
| 3 | Admin and support admin | Are delegated platform powers clear, useful, and correctly limited compared with owner authority? |
| 4 | Auditor | Can an auditor inspect evidence without mutation paths, hidden context, or misleading action affordances? |
| 5 | Merchant | Can a merchant create stock, connect to a warehouse, submit inbound stock, create/import orders, request allocation, resolve backorders/exceptions, and follow service/shipment outcomes? |
| 6 | Warehouse operator | Can a warehouse operator activate service, review/receive inbound stock, pick/pack/ship orders, report exceptions, adjust stock, and hand off service evidence? |
| 7 | Cross-system surfaces | Do notifications, outbox, audit, operational details, attention signals, and assistant records connect stakeholders instead of becoming isolated logs? |

## Gap Classification

Use these categories so the audit does not collapse into one large vague backlog:

| Category | Meaning | Required handling |
| --- | --- | --- |
| Product blocker | The intended stakeholder cannot complete their loop, or the loop points to the wrong owner. | Fix before V15.10 closeout. |
| Implementation bug | The intended contract is right, but code/state/UI does not execute it correctly. | Fix with focused tests. |
| Comprehension gap | The workflow works, but a capable user cannot tell what happened, why, or what to do next. | Fix copy/layout/action hierarchy where practical. |
| Test gap | Behavior is plausible but not proved. | Add focused backend, frontend, or browser proof. |
| Documentation gap | Durable docs do not match behavior or intended ownership. | Update roadmap, architecture docs, or this audit. |
| Script gap | Local setup, seed, smoke, quality, or browser-tour scripts do not prepare or prove the workflow they claim to support. | Update scripts or docs and run matching proof. |
| Pre-V16/V16/V17 deferred gap | The gap is professionalization, provider delivery, realtime, scale, monitoring, backup/restore, local deployment-readiness certification, or real deployment activation. | Record owner and proof needed in Pre-V16, V16, or V17, without blocking V15.10 unless it breaks local product intent. |
