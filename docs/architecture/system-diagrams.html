System Component Overview

MerHouse coordinates fulfillment work between merchants, warehouse providers, and platform operators through a Spring Boot API, a React/Vite operations console, a Neon PostgreSQL database, and a managed deployment lane.

Backend API

  • Spring Boot 4 with tenant-aware auth, BCrypt passwords, JWT sessions
  • 18 REST controllers under /api/v1
  • 44+ service classes for domain logic, allocation, outbox, notifications
  • Flyway-managed PostgreSQL schema with 23 incremental migrations
  • Transactional outbox with scheduled drain processor and carrier dispatch

Frontend Console

  • React + Vite operations console with role-gated routing
  • Public pages: login, sign-up, forgot password, how-to-use
  • Platform pages: admin overview, tenants, users, access requests, relationships, outbox, audit
  • Merchant pages: overview, inventory, orders with import
  • Warehouse page: receiving, fulfillment, shipments, exceptions, inventory
  • Shared pages: service accountability, notifications, account, detail pages

Database

  • PostgreSQL with pgcrypto extension for UUID generation
  • 37 tables across identity, inventory, fulfillment, service, reliability, and notification domains
  • Optimistic locking on warehouse inventory via version column
  • Composite unique constraints for authorization invariants
  • Operational read indexes for bounded dense queries

Deployment Infrastructure

  • Neon PostgreSQL for managed V17 data
  • Hugging Face Docker Space for the Spring backend
  • Firebase Hosting for the React frontend
  • GitHub Actions for CI/CD quality gates and release workflows
  • GitHub Releases for signed Android APK distribution
  • Docker Compose for local PostgreSQL + backend + nginx frontend

Realistic Operating Workflow

MerHouse coordinates work between a merchant, a warehouse provider, and platform reviewers. The happy path covers onboarding, relationship, inbound stock, demand, allocation, warehouse execution, evidence, alerts, service accountability, and review.

1. OnboardPlatform reviews access requests, creates tenants and users via approve-and-activate or separate approve-then-convert, and keeps support/auditor roles in review-safe boundaries.
2. ConnectMerchant requests provider service. Warehouse activates the relationship or platform governs suspend, reactivate, and end exceptions.
3. StockMerchant creates product records and sends inbound stock. Warehouse approves, receives with damaged/short evidence, rejects, or the merchant cancels.
4. FulfillMerchant creates order demand or imports batches. Stock is allocated to an authorized warehouse relationship, then picked, packed, shipped, or marked exceptional.
5. ReviewBoth parties inspect timelines, notifications, service statements, SLA status, disputes, claims, and accountability evidence before closing the work.

Story: A New Merchant Needs To Go Live

ActorOwner/admin reviews a public access request; support can watch the queue; auditor can inspect the decision later.
TensionThe requester needs an account, but duplicate emails, missing organization details, and accidental seed-style credentials must not slip through.
WorkPlatform approves or rejects the request. Approve-and-activate creates tenant and user in one transaction with auto-generated password. Separate convert preserves the approval trail with a distinct conversion actor.
DoneThe merchant logs in to a guided workspace, account-ready delivery history exists, and governance evidence is readable without exposing credentials.

Story: A Merchant Sends The First Pallet

ActorMerchant creates product records, picks an active warehouse relationship, and sends inbound stock to a provider warehouse.
TensionReal receiving is messy: quantities can be short, damaged, rejected, or partially received, and none of that should silently become clean available stock.
WorkWarehouse approves the inbound, records received and damaged quantities with receiving notes, and the system writes inventory movement and audit evidence.
DoneOnly received quantity becomes available warehouse inventory; the merchant sees the receiving evidence with damaged and short quantities.

Story: Demand Becomes Warehouse Work

ActorMerchant creates a single order or imports many rows; warehouse operators receive allocated work tied to authorized stock on an active relationship.
TensionStock may be insufficient, imported quantities may be invalid, and warehouse execution can hit exceptions after picking starts.
WorkThe system allocates what it can via relationship-aware stock, preserves backorder evidence, then warehouse records pick, pack, shipment with packages, and exception details.
DoneMerchant and warehouse share the same operational timeline: what shipped, what failed, what returned, and which exception still needs review.

Story: Partners Need A Service Record

ActorMerchant and warehouse agree on operating terms once the relationship is active; platform can inspect the record across tenants.
TensionThe product must capture accountability without pretending to be invoicing, payment collection, legal casework, or attachment storage.
WorkAgreements, rate cards, SLA policies, statements with line-level source references, disputes, claims, and review requests stay linked to the relationship and source records.
DoneBoth parties can review note-and-record evidence, resolve issues, finalize statements, and keep support/auditor users in read-only evidence mode.

Story: Something Needs Attention

ActorAny role may receive local alerts, but each delivery is scoped to the recipient and tenant that actually owns the next action.
TensionUnread work can be buried under history, provider email might be disabled, and background handoff failures still need a review surface.
WorkUnread local deliveries become the action inbox; outbox records preserve retry/dead-letter evidence; system records stay auditable with deterministic behavior.
DoneThe right person sees the next action, read history remains available, and provider delivery attempts are recorded as provider evidence when enabled.

Story: The Same Product Ships To Web And Android

ActorOperator deploys the React web app via Firebase Hosting, deploys the Spring backend to Hugging Face, and builds a signed Android APK against the deployed backend URL.
TensionScripts can pass while the real browser or installed app feels broken, slow, or misconfigured.
WorkLive browser review leads, supporting proof records follow, and Android wraps the same Capacitor frontend shell instead of creating a second product.
DoneV17 proof shows deployed web and visible installed Android behavior before release evidence is attached to a cutover package.

Workflow Detail: What Actually Happens

Access And Account Lifecycle

Public access requests become reviewed onboarding work. Approval can create tenant and user records through approve-and-activate or separate approve-then-convert steps.

  • 6 roles: OWNER, ADMIN, SUPPORT_ADMIN, AUDITOR, MERCHANT, WAREHOUSE_OPERATOR
  • empty accounts see guided first-run states
  • owner/admin controls role, tenant, enabled state, and conversion
  • each signed-in user can inspect account context and change their password with current-password verification
  • reset-link recovery uses token-hash flow with throttling and generic responses

Inbound Stock To Available Inventory

The merchant owns goods and requests a provider warehouse to receive them. Only received quantity becomes available warehouse inventory.

  • draft and submitted requests keep merchant intent visible
  • warehouse approval starts receiving work
  • received, damaged, short, rejected, and cancelled states remain evidence
  • inventory audit logs capture quantity changes with actor context and reason codes
  • warehouse inventory uses optimistic locking via version column

Order Fulfillment

Orders allocate against authorized stock for an active relationship. Warehouse execution creates shipment, package, event, and exception evidence.

  • partial allocation creates allocation items and backorder items
  • warehouse operators progress allocations through pick, pack, and ship work with scan codes and priority
  • shipments carry carrier, tracking number, status, and package evidence with dimensions
  • exceptions stay linked to the allocation, shipment, merchant, and provider parties
  • order import batches support all-or-none or partial-accept modes

Service Accountability

Service records describe operating terms and evidence, not billing or legal settlement. They keep the merchant/provider relationship reviewable.

  • agreements with versioned terms, rate cards, and SLA policies attach to active relationships
  • statements with line-level source references summarize local service units
  • claims, disputes, and review requests preserve note-and-record evidence
  • support and auditor roles review the evidence without service mutation controls

Notifications, Outbox

Operational handoffs create recipient-scoped local alerts. Reliability records make asynchronous work and review assistance visible.

  • 4 topics: ACCOUNT_LIFECYCLE, OPERATIONS, SERVICE_ACCOUNTABILITY, OUTBOX_HEALTH
  • 1 channel: IN_APP (local delivery only)
  • unread local deliveries are an action inbox; mixed delivery records remain history
  • outbox events with retry/dead-letter and carrier dispatch records

Web, Android, And Release Proof

The React product shell is shared by desktop web, narrow web, and Android packaging via Capacitor. The V17 release lane deploys the same product.

  • web runtime deployed through Firebase Hosting
  • backend runtime packaged for Hugging Face Docker Space
  • data in Neon PostgreSQL for the managed lane
  • signed Android APK delivery through GitHub Releases after live proof
  • Docker Compose for local PostgreSQL, Spring backend, and nginx-served frontend

State Machines

These are the states operators actually see and reason about, matching the database CHECK constraints and service-layer transitions across all 23 migrations.

Access Request

Pending Approved or Rejected Converted (from Approved)

Approve-and-activate combines approval and conversion in one step. Separate approve then convert preserves the reviewer trail. Throttled by requester email.

Relationship

Requested Active Suspended Ended

Warehouse can activate requested work. Platform governance owns suspend, reactivate, and end. Only active relationships allow inbound and allocation.

Inbound Stock

Draft Submitted Approved Receiving Received or Rejected

Cancelled can branch before completion. Damaged and short quantities remain evidence. Only received quantity becomes available warehouse inventory.

Fulfillment Allocation

Pending Picking Packed Shipped

Cancelled can branch from Pending or Picking. Shipment creation moves allocation from Packed to Shipped and order to Shipped.

Customer Order

Created Allocated or Partially Allocated or Backordered Shipped Delivered

Cancelled can branch from Created, Allocated, Partially Allocated, or Backordered. Cancellation releases reserved stock and cancels open backorders.

Shipment

In Transit Delivered, Failed, or Returned

Delivered moves the order to Delivered. Failed and Returned keep the order in Shipped for later operational handling.

Shipment Package

Packed Handed Off Delivered, Failed, or Returned

Package events record handoff, delivery, and exception evidence against individual packages within a shipment.

Service Agreement

Draft Proposed Active Suspended, Ended, or Superseded

Review requests stay locked until agreement is active. Versioned with supersedes link. Statements remain service-unit evidence, not invoices.

Service Statement

Draft Finalized Marked Settled or Disputed or Cancelled

Finalized statements can be marked settled (coordination marker, not payment proof) or disputed. Lines reference source operational records.

Dispute / Claim / Review

Open / Pending Resolved / Approved or Rejected

Disputes and claims use OPEN/RESOLVED/REJECTED. Review requests use PENDING/APPROVED/REJECTED. Note-and-record evidence only, no attachment storage.

Outbox Event

Pending Processed Failed (retryable) Dead Letter

Scheduled processor drains pending rows. Failed rows increment attempts and receive next_attempt_at. Retryable failures retry until max attempts, then dead-letter.

Notification Delivery

Prepared Local Recorded or Skipped By Preference Unread Action or History Read Provider Recorded (when SMTP enabled)

Action inbox is recipient-scoped. Provider delivery is evidence only after V17 SMTP proof. Provider statuses: NOT_CONFIGURED, READY_FOR_PROVIDER, SENT, FAILED.

Backorder Item

Open Fulfilled or Cancelled

Fulfilled closes the shortage evidence but does not create reserved stock or an ALLOCATED order status. Cancelling an order cancels its open backorders.

Fulfillment Exception

Open Resolved

Linked to allocation and/or shipment. Merchant can resolve; warehouse and platform can also resolve. Resolution note preserved as evidence.

Runtime And Release Shape

Local Certified Shape

Local proof keeps the product coherent while V17 deployed evidence gates production claims.

  • Docker Compose runs PostgreSQL, Spring backend, and nginx-served frontend for local review
  • browser tours and installed Android tours verify the same stakeholder workflows
  • proof reports support live review but do not replace it
  • shared mobile shell proof rejects duplicate product behavior inside the Android wrapper
  • Capacitor wraps the same React build output (frontend/dist) for Android

V17 Managed Deployment Lane

The current deployed lane keeps the first release simple and stable.

  • Neon PostgreSQL for managed data
  • Hugging Face Docker Space for the Spring backend
  • Firebase Hosting for the React frontend
  • GitHub Actions for CI/CD quality gates (merhouse-quality-gate.yml) and Android release (merhouse-android-release.yml)
  • GitHub Releases for signed internal APK distribution
  • SMTP email delivery when MERHOUSE_EMAIL_ENABLED=true with provider credentials externalized

Backend Configuration Boundary

Production safety validates deployment configuration at startup.

  • MERHOUSE_DEPLOYMENT_PUBLIC=true triggers public safety checks
  • recovery throttling via MERHOUSE_AUTH_RECOVERY_REQUEST_LIMIT and window
  • access request throttling via MERHOUSE_ACCESS_REQUEST_LIMIT and window
  • email provider credentials must be externalized; no checked-in SMTP secrets
  • reset token echo disabled in public environments

Notification And Email Direction

In-app alerts are the action inbox. SMTP email is opt-in provider evidence.

  • 4 topics: ACCOUNT_LIFECYCLE, OPERATIONS, SERVICE_ACCOUNTABILITY, OUTBOX_HEALTH
  • 1 channel: IN_APP (local delivery only)
  • local deliveries are recipient-scoped with source navigation to operational detail pages
  • provider delivery attempts record status, timestamps, error, and retry count
  • SMS, phone OS push, lock-screen, and notification-tray are out of scope
