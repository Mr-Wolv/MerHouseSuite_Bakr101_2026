Workflow Cards: Use Cases, Scenarios, And Stories

1. Platform Onboards A Merchant

A public request becomes a governed tenant and login, with review state kept visible to platform users.

TriggerA company submits an access request with organization, email, requested role, and notes; copied whitespace is normalized before validation, pending duplicate emails are rejected, and repeated requester emails are throttled.
FlowThe request is reviewed, accepted, and converted into an organization account with an initial user.
OutcomeThe requester can log in, and conversion links remain on the access request record.
Request -> approval -> tenant + user

2. Merchant Sends Stock To A Provider

The merchant establishes the service lane before provider inventory can become usable for demand.

TriggerA merchant creates an item, connects to a warehouse provider, and submits an inbound stock request.
FlowThe provider relationship is activated, inbound stock is submitted, approved, received, and reconciled.
OutcomeReceived quantity becomes warehouse inventory; damaged and short quantities stay visible on the inbound record.
Relationship -> inbound -> authorized stock

3. Warehouse Fulfills Customer Demand

Orders turn authorized stock into warehouse work, shipment evidence, and customer-visible progress.

TriggerA merchant creates orders or imports pasted rows with positive whole-number quantities for stocked items.
FlowThe order is allocated to authorized stock, assigned as warehouse work, picked, packed, and shipped.
OutcomeAllocated stock is reserved, packages are recorded, exceptions can be reported or resolved, and fulfilled backorders close shortage evidence without pretending an allocation exists.
Order -> allocation -> package evidence

4. Partners Reconcile Service Work

The system records service accountability without collecting payments or pretending to be accounting software.

TriggerA merchant and provider need shared evidence for receiving, storage, pick-pack, shipment handoff, or exceptions.
FlowThe agreement is drafted, proposed, accepted, and later used to produce service statements from operational evidence.
OutcomeStatements, SLA rows, disputes, claims, and review requests preserve the service record.
Agreement -> statement -> dispute/claim/review

5. Platform Governs And Recovers

Owner, admin, support-admin, and auditor roles observe or act according to their operational responsibility.

TriggerA tenant, relationship, user, outbox event, or access request needs inspection or intervention.
FlowThe platform reviews health, governs tenants and relationships, supports users, and monitors background work.
OutcomeGovernance actions are visible in audit events, and lower-privilege roles stay constrained.
Governance action -> audit + recovery trail

6. Users See Local Action Alerts

V13-V16.2 record account-lifecycle and operational alert history without connecting to external email, SMS, phone OS push, lock-screen, notification-tray, or webhook providers.

TriggerAn enabled user requests a password reset, or an approved access request is converted into an account.
FlowThe system stores recipient-scoped notification deliveries for lifecycle, operations, service-accountability, and outbox-health events, then refreshes the app-shell Alerts badge through lightweight polling.
OutcomeThe recipient sees an action inbox, local delivery history, provider status, preference state, and read state without cross-user visibility; V17 email attempts are delivery evidence, not unread in-app actions.
Lifecycle or operations event -> local alert -> Alerts badge

7. Users Ask For Scoped Assistance

V14 starts with deterministic assistant summaries, risk-ranked review suggestions, and refusal records; V17 separates that behavior behind a read-plus-draft runtime interface before any later provider-backed AI activation.

TriggerA platform, merchant, or warehouse user asks for an operational summary or review-only suggestion.
FlowAssistantService checks role and tenant scope, passes a bounded request to AssistantRuntime, reads only authorized local services, ranks the allowed risk metrics, records the interaction, and keeps suggestion decisions explicit.
OutcomeSummaries, reasoned suggestions, refusals, and accept/reject decisions are visible in the user's assistant history and platform audit trail.
Prompt -> scope check -> response + history + audit; decision -> audit

8. Users Maintain Account Security

V16 introduced authenticated account settings for local account context, copied-email normalization on public auth routes, and current-password-verified password changes.

TriggerA signed-in user opens their topbar identity and reviews account, role, tenant, enabled-state, and local delivery-boundary context.
FlowThe user submits current password and a valid new password through PATCH /api/v1/auth/me/password.
OutcomeThe password hash changes, a USER_PASSWORD_CHANGED audit event is recorded, and email, role, tenant, and enabled-state governance remain platform-managed.
Account page -> password verification -> audit event

9. The Same App Runs In Web And Android

V16.1 packages the existing React shell as a local Android debug APK through Capacitor without adding duplicate mobile workflows.

TriggerA local operator builds the frontend, syncs it into the Android wrapper, and installs the debug APK on an emulator.
FlowThe APK WebView uses the same routes, API client, role model, account settings, notifications, and attention-first workflows as the web app.
OutcomeNative and web proof scripts tour the same product behavior; app-store release, native OS notification delivery, push provider rollout, barcode/camera APIs, and offline sync remain future work.
React build -> Capacitor sync -> installed APK tour + web tour

10. Bug Hunts Drive Convergence

V16.2 keeps Android, web, code, tests, scripts, docs, and diagrams aligned through focused bug hunts and wrap-up certification rather than repetitive proof churn.

TriggerA reviewer starts with the roadmap QC rules, the latest bug-hunt ledger entry, and one concrete file, workflow, dense-state, permission, or frontend/backend contract risk.
FlowThe suspected bug is inspected from code, browser behavior, installed-APK behavior, reports, or gate output; only evidenced defects are fixed, then covered with focused tests before broader gates are rerun when needed.
OutcomeEach bug-hunt entry records the defect class, affected files, tests, scripts, docs, diagram impact, remaining risk, and next file-audit target; the V16.2 closeout records the reviewer/product-owner live browser and installed-app walkthrough in the convergence ledger.
Live/code evidence -> concrete bug -> focused fix -> proof + docs/diagram update -> final walkthrough

Current Route, API, And Read-Model Surface

These cards summarize the current React router, Spring web controllers, and derived attention model. Attention signals are not database tables; they are additive read-model fields derived from existing records and returned by role-scoped summary endpoints.

Public And Account Routes

Public access

/login/forgot-password/reset-password/request-access
  • Public users can sign in, request account access, and request local password-recovery proof without provider-delivery claims; reset requests are throttled per enabled account, and reset confirmation tolerates copied-token whitespace while preserving the new password value exactly.

Signed-in account

/accountGET /api/v1/auth/mePATCH /api/v1/auth/me/password
  • Every authenticated role can inspect account context and change their own password after current-password verification.

Authenticated route guard

/*RouteErrorPageNotFoundPage
  • The authenticated router redirects each role to its workspace and catches unavailable deep links with MerHouse guidance instead of framework error copy.
AuthController owns login, current-user, reset, and self password change AccessRequestController owns public request submission and platform review

Platform Governance Routes

Platform console

/admin/admin/tenants/admin/users/admin/access-requests
  • Owner/admin roles govern organizations, user accounts, public onboarding, and platform attention queues; the primary admin summary renders independently from slower orders and tenant-health ledgers so dense local proof data does not block the overview. Support-admin can review and recover supported accounts, auditor is read-only, and copied admin text fields normalize before validation while passwords remain exact.

Evidence and reliability

/admin/relationships/admin/outbox/admin/audit
  • Relationship governance, role-aware outbox diagnostics, carrier-dispatch records, and privileged audit events remain separate from daily merchant/warehouse execution; support/auditor roles review relationship state without suspend/reactivate/end controls.
AdminControlController returns summary, tenant health, and audit events TenantController, AdminUserController, AdminOutboxController, and MerchantWarehouseController own platform mutations with owner/admin method guards; AdminOutboxController and relationship governance expose read-only diagnostics to support/auditor roles

Merchant Routes

Merchant operations

/merchant/merchant/inventory/merchant/orders
  • Merchants manage stock readiness, warehouse relationships, inbound requests, customer contacts, orders, imports, allocation, backorders, and exception follow-up; copied merchant text fields normalize before validation, inbound stock quantities, order quantities, draft order line quantities, and pasted import quantities must be positive whole numbers before submission, dense order queues disclose additional matching orders explicitly, and fulfilled backorders do not synthesize allocation state.

Merchant evidence routes

/orders/:orderId/inventory/items/:inventoryItemId/merchant-warehouse/relationships/:relationshipId
  • Detail routes show role-scoped operational timelines and linked records instead of exposing cross-tenant data; denied or missing detail records show role-aware recovery links and role-appropriate recovery copy, including platform-safe inventory-detail recovery and shared warehouse-work detail recovery for merchant, warehouse, and platform roles, and relationship detail loads fulfillment allocations through a merchant/provider-scoped query rather than scanning all allocations.
DashboardController returns merchant attention and summary metrics InventoryController, OrderController, and MerchantWarehouseController own merchant work

Warehouse Routes

Warehouse execution

/warehouse/inbound-stock-requests/:inboundStockRequestId/fulfillment-allocations/:allocationId/shipments/:shipmentId
  • Warehouse operators activate relationships, approve and receive inbound stock, pick, pack, ship, deliver, fail, return, and report exceptions; shared web/native receiving controls capture whole-number received quantity, whole-number damaged quantity, and receiving-note evidence before posting receipt; shared shipment controls require whole-number package count and dimensions while keeping package weight decimal-capable; copied warehouse evidence text normalizes before validation while quantities, dimensions, priorities, statuses, and ids stay structured, and dense fulfillment and shipment queues disclose additional work explicitly.

Warehouse APIs

GET /api/v1/dashboard/warehouseGET/POST /api/v1/warehousesPATCH /api/v1/fulfillment-allocations/{id}/statusPOST/PATCH /api/v1/shipments
  • Warehouse work is scoped to authorized provider relationships and warehouse inventory records; shipment, scan, adjustment, exception, receiving, and rejection text trim at the shared route and API boundary.
FulfillmentController owns allocation, shipment, package, and exception paths OperationalDetailController owns role-scoped evidence pages for warehouse work

Shared Review Routes

Service, assistant, and alerts

/service-accountability/assistant/notifications
  • All authenticated roles can reach shared review surfaces, but service methods, assistant scopes, and notification reads stay role- and tenant-scoped; allowed stakeholders can finalize draft statements, mark finalized statements settled, resolve or reject open disputes/claims, and approve or reject pending reviews, while support-admin and auditor inspect service evidence without mutation authority. Review-request retries clear stale success feedback before showing a failure, and unread service-review-request alerts render as action-needed local inbox work.

ERD Cards: UML From Current Database Schema

These cards summarize the Flyway schema through migration 17. Each entity card lists the relationship-defining columns and the important connections without drawing every line across the page. Account settings and attention signals introduced in V16 do not add tables; they use `app_users`, `admin_audit_events`, and derived summary DTOs.
